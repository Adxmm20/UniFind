# UniFind agent notes

Single-page Next.js 16 (App Router), React 19, Turbopack. Styling is Material UI v9 + Emotion only — Tailwind was fully removed.

## Commands
- `npm run dev` — dev server on port 3000, host 0.0.0.0
- `npm run build` — production build (Turbopack)
- `npm run lint` — eslint (nextVitals + nextTs rules)
- `npm run db:seed` — create `data/unifind.db` from `db/schema.sql` + `db/seed.sql` using `node:sqlite` (no deps). **Non-destructive**: if the database already exists it is left alone, so accounts signed up at runtime survive.
- `npm run db:reset` — drop and recreate every table (`db:seed --force`). Use this when the schema/seed changes or you want a pristine database.

`predev`/`prebuild` run the non-destructive seed automatically. Because it now only seeds a missing database, a stale database is *not* repaired for you — run `db:reset` after editing `db/schema.sql` or `db/seed.sql`. Requires Node ≥ 22.5 (`node:sqlite`); developed on Node 24.

No test script, no CI workflows, no pre-commit hooks.

## Architecture (read before touching styling)
- `app/layout.tsx` — Server Component. Owns `<html>`/`<body>`, `metadata` export, `next/font` Geist, and the accessibility chain. Must stay a Server Component: `metadata` cannot be exported from `"use client"`. It reads the `unifind_prefs` cookie and spreads `prefsAttributes(prefs)` onto `<html>`, so the theme/filter/text-size state is already in the first byte of HTML (no pre-paint script, no flash); renders the skip link first in the body; then `AppRouterCacheProvider` → `AccessibilityProvider` (client) → `ScrollWallpaper` + `<div className="page-shell">{children}</div>`. The shell is the element the colour filters are applied to — see *Accessibility tools*.
- `app/components/Header.tsx` — `"use client"`. All the UI (`AppBar` — `position="sticky"`, see below — `Drawer`, `TextField`, …), rendered by every page directly under `<body>`. The search box is a `Box role="search"` wrapping a MUI **`Autocomplete`** combobox: typing asks `/api/suggest` for as-you-type suggestions, its magnifier is a plain `IconButton` (there is no form left to submit), and free text pushes `/search?q=…` (see *Search*). It no longer owns a `ThemeProvider` — the MUI theme comes from `AccessibilityProvider` above it (see *Accessibility tools*) — but it still renders `CssBaseline` with `enableColorScheme={false}`, because `color-scheme` is what resolves every token in globals.css and MUI writing its own would fight the preference the server already rendered. Takes `user: SessionUser | null`; when it is `null` the visitor is a **guest**, who browses the site exactly as usual but sees a guest drawer panel, no `Profile` link, and `Bookmark`/`Post` items that open the login prompt. Signing in swaps the drawer summary to `MiniProfile` and reveals `Profile`, `Post` (→ `/post`), `About` and `Logout`. `About` (icon `infoProfile`, → `/about`) is the one drawer row that is plain navigation rather than an account action: it closes the content rows above `Logout`, and sits last for a guest, who has no `Logout` to be above. The drawer is `MiniProfile`/`GuestPanel` → `Divider` → `List component="nav" aria-label="Main"` (each row closes the drawer itself) → `Divider` → `AccessibilityPanel`. Its one effect listens for both the `unifind:auth-prompt` event and **Alt+A**, which opens the drawer — the shortcut for the accessibility panel.
- `lib/db.ts` — `node:sqlite` (`DatabaseSync`) singletons over `data/unifind.db` (override with `UNIFIND_DB_PATH`). `getDb()` is **read-only** and is all page rendering ever uses; `getWriteDb()` is read-write and is used *only* by the three things that write at runtime — auth (signup), bookmark toggles and posting. Server-only; never import from a client.
- `lib/auth.ts` — server-only auth. scrypt password hashing and a signed (`httpOnly`) session cookie via `node:crypto` — no runtime dependencies. `getSessionUser()` reads the cookie and resolves it against the DB; `authenticate` / `register` / `createSession` / `destroySession` do the rest. `SessionUser` is `{ email, username, phone }`, where `username` is the email local-part (same convention as `USERNAME_SQL` in `lib/queries.ts`).
- `app/actions/auth.ts` — `"use server"`. `loginAction` / `signupAction` / `logoutAction`, called directly from `LoginDialog.tsx` and `Header.tsx`. They return `AuthFormState` (`{ error, ok }`); the client shows `error` inline and the dialog closes itself once `ok` is true.
- `app/components/auth/LoginDialog.tsx` — `"use client"`. The one and only login/signup UI: a centred, desktop-style MUI `Dialog`, never a route. Split 35/65 — a solid theme-green sidebar (`--surface-green`) with the wordmark on the left, the stacked form on the right (`--surface-3`; bold `LOGIN` header, `variant="standard"` underline fields, a minimal underlined submit, the sign-up link, and the social row pinned bottom-right). Below `sm` the sidebar collapses and the card goes full-width. The view (Log in / Sign up) is controlled by `Header` so a trigger can pick it. `app/components/auth/GuestPanel.tsx` is the drawer summary shown to guests; `app/components/auth/SocialIcons.tsx` is the four brand marks (Apple, Google, Facebook, TikTok) inlined as SVG — `fill="currentColor"`, `aria-hidden`, and not focusable, because social sign-in is not wired up.
- `lib/queries.ts` — typed read helpers for every table (`getEvents`, `getRentals`, `getServices`, `getEventById`, `getItemById`, `getUserByUsername`, `getAllUsernames`, `getEventsByOrganizer`, `getItemsByProvider`, `getReviewsForProvider`, `getBookmarksForUser`, `getRsvpsForUser`, …). All synchronous, no ORM. It holds **no search SQL** any more — search reads these helpers and scores the rows in `lib/search.ts` (see *Search*).
- `app/components/cardData.ts` — server-only, and the **one** place a database row becomes the `CardData` `ItemCard` renders (`eventCards()`, `itemCards()`) plus `bookmarkState(user, savedIds)`, which builds the per-card `{ signedIn, saved }` the bookmark control needs so no page invents its own. Both card builders take an optional fourth `note` callback — the search page's "by josa_organizer" — which is the only way a card may differ between surfaces. Shared by the home grid, the search results and the profile page, so a record cannot look different depending on where it was found — see *Search*. `BookmarkState` is the callback type every page kind passes in. It also fills the three **facet facts** the home toolbar reads and no card displays: `category` (kept apart from `subtitle` even though both come from the same column, so a card whose second line ever says something else cannot break the filter) and `startTime` / `price` (only an event has one, only an item the other — the same facts `BookmarkCard` used to declare for itself). (The bookmarks page is the one deliberate exception to *this* mapping: its rows carry extra per-link fields — `bookmarkedAt`, `bookmarkId` — so `app/bookmarks/page.tsx` maps them itself into `BookmarkCard`, which extends `CardData`.)
- `lib/searchText.ts` — pure matching rules, no database, Node or React import: `termsOf(query)`, `scoreText(text, term)` (3 verbatim / 2 shared stem / 1 one edit away), `hitsAll`, `handleOf(email)` and the `MIN_QUERY_LENGTH` the header reads. Shared by the server (results, suggestions) and the client (the fetch threshold) precisely so the rules cannot diverge.
- `lib/search.ts` — server-only search: `searchCatalogue(query)` (ranked `events` / `items` / `people` plus the parsed terms), `suggest(query)` (the as-you-type list) and `kindOf(item)`. It scores rows in JS rather than in SQL — see *Search* for why, and for what has to change if the catalogue ever grows.
- `app/api/suggest/route.ts` — `GET /api/suggest?q=…`, the one route handler, behind the header's search box. See *Search*.
- `app/page.tsx` — Server Component. Reads events/items from SQLite via `lib/queries`, merges in local images from `public/img/` (`fs.readdirSync`), then renders `<Header />`, `<Slideshow />`, and a `<Suspense>`-wrapped **Events/Rentals/Services** grid of `HomeTabs` `CardData`. Every row becomes a card through `app/components/cardData.ts` — the one mapping, shared with the search results and the profile page, so a record cannot look different depending on where it was found; rentals and services go through the *same* `itemCards()`, so they cannot drift apart either. `getServices()` is `getRentals()`'s `item_type='service'` sibling and `itemImageIndex()` already resolves both picture folders. The tabs are split: `app/components/HomeTabs.tsx` is the bar + filter/sort pills + grid (also the prerendered Suspense fallback) and reads its list from a `Record<HomeTab, CardData[]>` lookup, and `app/components/HomeTabsUrl.tsx` reads/writes `?tab=` via `useSearchParams` (why the `Suspense` boundary is required). `app/components/ItemCard.tsx` renders a card, showing a blank placeholder when `image` is absent. The whole card stays clickable through a **stretched link** (`position:absolute; inset:0`) rather than a wrapping `<Link>`, which leaves room for the bookmark button as a *sibling* of that link — an `<a>` may not contain a `<button>`.
- **Home grid filtering & sorting** — the two pill `Select`s that sit **inside the tab panel**, directly under the tab strip. Like the bookmarks toolbar they are plain local state, not URL parameters (all three lists arrive as props, so there is no round trip and no `Suspense` boundary — the tab itself is the exception), and they are held **per tab**, which is why nothing ever has to be reset: each tab's category list and its sort options belong to that tab, so a selection cannot be invalid — the situation `BookmarksView` has to handle by resetting a stale sort in the change handler. The **filter** offers exactly the categories the active tab's own cards carry (`card.category`), so it cannot drift from the catalogue and every option matches at least one card; it renders nothing when a tab has one category or none. The **sort** options follow the tab, because the two record kinds sort on different columns: events get `Soonest` / `Latest` / `Title A–Z`, rentals and services get `Default` / `Price: low to high` / `Price: high to low` / `Title A–Z` (the raw number, as `BookmarksView` sorts too — price units are not convertible). `Default`/`Soonest` is the *no-op*: it returns the server's order untouched (`getEvents()` is already `start_time`-ordered, items arrive in `item_id` order), so no card moves until a visitor picks something. Two hydration rules follow: the derived category list is ordered with a plain code-unit comparator and the no-op sort compares nothing, so **the first client render is byte-identical to the server markup**; the one `localeCompare` (the `Title A–Z` sort) is safe precisely because a default sort can never reach it. Both pills sit together at the **right-hand end** of the row (wrapping as a pair on a narrow screen) and carry their own glyph — `filter`'s funnel and `sort`'s up/down arrows, passed as a **`startAdornment`** wrapped in an `InputAdornment`, which is what insets the pill's content and spaces the glyph against the label; the ink is set on the adornment because `AppIcon` paints through a mask with `currentColor` and MUI's own adornment colour is a palette grey. Both pills use `pillSelectSx` from `formStyles.ts`, shared with the bookmarks toolbar.
- `app/[username]/page.tsx` — Server Component dynamic route. Resolves the user by email local-part, then reads their events/listings/reviews. Events and listings go through the same `eventCards()` / `itemCards()` mapping as the home grid (see `cardData.ts`), so their pictures resolve by stem exactly like everywhere else. The page originally hand-built its `CardData` and so never set `image`, which left every profile event card a blank rectangle — do not go back to building cards here. (Reviews stay hand-built: a review has no picture and no bookmark.) `generateStaticParams` prerenders every username from the DB; unknown usernames render on demand and hit `notFound()`.
- `proxy.ts` — request-time Proxy (Next 16 defaults it to the Node.js runtime, so `node:sqlite` works). It runs *before* the render, so it can return a real **404** for unknown usernames by rewriting to `/__not-found__/404` (the page's own `notFound()` only yields a streamed 200 under PPR). Matcher skips `_next/`, `img/`, `bookmarks`, `post`, `search` and `about` (`post(?:/|$)` / `search(?:/|$)` / `about(?:/|$)` rather than a bare prefix, so an unrelated username like `/postman`, `/searchlight` or `/aboutman` still resolves; `bookmarks` predates that worry), and dotted asset paths. Every *other* single-segment path is treated as a profile username, so **a new top-level route must be added to that pattern** or the proxy will look up a user of that name, fail, and rewrite the page to a 404. (A route *under* a prefix — `app/api/suggest` — needs no entry: the username branch only ever sees single-segment paths.)
- `app/not-found.tsx` — styled 404 (MUI + `Header`), rendered both by the proxy rewrite and by `notFound()`.
- `app/about/page.tsx` — the About page, and the only fully static route: no query, no client component, no state — just `getSessionUser()` for the header plus hardcoded copy. One ABOUT `Card` (an `h1` and the paragraph to edit) above a three-across grid (`1fr` under `sm`) of team cards — a 72px circular `next/image` avatar from `public/img/pfp/<Name>.jpeg` (each file is named after its person, so a row and its picture are matched by eye; `objectFit: cover` with a shared top-third `objectPosition`, because both portrait shots carry the face high while the landscape one is only trimmed at the sides; the avatar is decorative, `alt=""`, since the name sits right underneath), role, `Divider`, name, email — all on the `--surface-2`/`--ink*` tokens, so high contrast frames each card with every other Paper. The `TEAM` array at the top of the file is the only thing to edit. `/about` is a top-level route, so it needed its proxy matcher entry like every other one (see `proxy.ts`).
- `app/components/profile/` — `"use client"` profile UI (`ProfilePage`, `ProfileSidebar`, `ProfileTabs`); all data is passed in from the Server Component. `MiniProfile.tsx` (the `Header.tsx` drawer summary) shows the **signed-in** `SessionUser`, not the profile being viewed.
- `app/components/details/` — `"use client"` details UI, the profile pattern again: `DetailsView.tsx` owns the two-column grid (gallery left; kind eyebrow, underlined title, bookmark control and the pill row right) plus the three bars — **Description** (open by default), **Details** (label/value rows) and **Organiser**/**Provider** (`kind === "Event"` picks the label) — all MUI `Accordion`s with a `--surface-2` surface, a hairline border and the inline `ChevronDown`. `ImageGallery.tsx` is **data-driven**: one picture renders a plain hero, and the next-image scrim, its arrow and the thumbnail strip appear by themselves once a record carries more than one (nothing is faked to fill the mock's five slots). `Chevron.tsx` holds the only two inline chevrons. The bars keep `--ink`/`--ink-muted` on their own surface and the pills use `--pill-bg`/`--pill-ink`; only the eyebrow and title use `--on-bg*`, because they are the only text sitting on the wallpaper.
- `app/bookmarks/page.tsx` — Server Component. Guests get `BookmarksGuest` (a centred panel with its own `LoginDialog` instance); signed-in visitors get `BookmarksView`. Every card here is `bookmark: { signedIn: true, saved: true }`, since a row on this page is saved by definition.
- `app/components/bookmarks/BookmarksView.tsx` — `"use client"`. Owns the three toolbar controls: a pill `Select` filtering All/Events/Rentals/Services, a second pill `Select` whose options **follow the filter** (only an event has a start time, only a rental or service has a price, so "All" offers just the keys every kind shares), and an `IconButton` toggling grid/list. All three are local state, not URL params — the data is already loaded, so there is no round trip and no `Suspense` boundary (unlike `HomeTabsUrl`; the home grid's own filter/sort pills work the same way). A filter change that invalidates the current sort resets it in the change handler, never an effect. Rentals and services both arrive as items, so the page splits them on `item_type` and passes the two arrays separately. The pills share `pillSelectSx` with the home toolbar, and `startTime`/`price` — what the "Event date" and "Price" sorts order on — come from `CardData` rather than being redeclared here. `app/components/ItemRow.tsx` is the list-view counterpart to `ItemCard`.
- `app/components/bookmarks/BookmarkButton.tsx` — `"use client"`. The bookmark control, **hidden until the card is hovered**: `opacity: 0` + `pointer-events: none`, revealed by `.MuiCard-root:hover &, .MuiCard-root:focus-within &`, and always visible under `@media (hover: none)` since touch has no hover state. `pointer-events` moves with `opacity` — an invisible button that still takes clicks is a trap sitting on top of the card. `focus-within` keeps it reachable by keyboard. A guest gets the same control with `signedIn: false`; clicking it raises the login prompt rather than writing. `variant="overlay"` (default) is that card control; `variant="inline"` drops the absolute corner and the hover-reveal for surfaces that are not a card — the details page passes it, since there is nothing to hover there.
- `app/components/auth/authPrompt.ts` — `"use client"`. `openAuthPrompt(tab)` dispatches a `unifind:auth-prompt` window event, which `Header` listens for. A bookmark button sits outside Header's subtree and `CardData` crosses the Server → Client boundary, so it can reach the dialog's state neither by props nor by callback; a window event is the smallest bridge that works without hoisting the dialog into a provider above the pages (see the gotcha below).
- `lib/bookmarks.ts` — server-only bookmark reads/writes. `getBookmarkIds(email)` returns a `Set` of record ids for a whole page in one query. `getBookmarkedEvents`/`getBookmarkedItems` are two joins (a row points at an event *or* an item) that also select `bookmark_id`, because `created_at` only resolves to the second and the id is the sole tiebreaker — the client sorts on the same pair so the merged "recently bookmarked" order matches the query's. `toggleBookmark` validates the target itself: `PRAGMA foreign_keys = ON` lives in `db/schema.sql` and applies only to the connection that ran it, so the write connection does **not** enforce the `REFERENCES`. There is no unique index on `(user_email, event_id)` — adding one means a schema change and `db:reset`, which would drop accounts created at runtime — so duplicates are cleaned up by the delete instead.
- `app/actions/bookmarks.ts` — `"use server"`. `toggleBookmarkAction(recordId)` reads the session and delegates to `lib/bookmarks.ts`, mirroring the auth split.
- `app/post/page.tsx` — the one page for posting. Server Component: a guest gets `PostGuest` (the bookmarks gate again), a signed-in visitor gets `PostForm` fed with the **existing** vocabulary (`getEventCategories` / `getItemCategories` / `getPriceUnits`), so a new record cannot invent a near-duplicate category.
- `app/components/post/PostForm.tsx` — `"use client"`. One form, three kinds: the Event / Rental / Service tab strip is local state, and only the mounted type's fields are submitted (a hidden `type` input carries the choice; the two groups are keyed so switching types cannot leak a typed value into a reused uncontrolled input). The category `Select` lists that type's existing names plus `Other…` — a `CATEGORY_OTHER` sentinel that makes the action read the sibling `categoryOther` field. The picture control is a hidden file input behind a `pictureAdd` button that shows the chosen name (no object-URL preview, so there is no effect to clean up). Submit calls the action from the submit handler and pushes to the new record's details page, keeping the button disabled through the navigation.
- `app/components/post/PostGuest.tsx` — the gate for a guest who opens `/post` directly; the drawer's Post row opens the login prompt instead.
- `app/components/formStyles.ts` — the single home for the site's underline field look (`fieldSx`), shared by `LoginDialog` and `PostForm` so the two cannot drift, and for the **pill select** (`pillSelectSx`), shared by the bookmarks toolbar and the home filter/sort bar.
- `lib/postTypes.ts` — the client/server contract: the `PostType` union and `CATEGORY_OTHER`. It lives apart from `lib/posts.ts` because that module touches `node:fs` and must never reach a Client Component.
- `lib/posts.ts` — server-only **write** path for posting: `createEvent` / `createItem` validate, insert over `getWriteDb()`, write the picture and return the new `event-N` / `item-N`. The third runtime writer — see *Posting*.
- `app/actions/posts.ts` — `"use server"`. `createPostAction(formData)`: read the session, delegate, return `{ ok: true, recordId }` or `{ ok: false, error }`, the same wrapper shape as the auth and bookmark actions.
- `lib/images.ts` — server-only `listImages()` / `imageIndex()` (base name → public URL), shared by `app/page.tsx`, the search page, the profile page and the bookmarks page so a card's picture resolves identically wherever it is rendered.
- `lib/format.ts` — pure presentation helpers, imported by both Server Components and client views: `priceLabel`, `formatDate`, `formatDateTime` and `formatEventRange` (the event pill reads "18 Oct 2026, 08:30 – 13:00", collapsing to the full timestamps when start and end fall on different days). All UTC and fixed-locale so server and client strings cannot drift (hydration); an unparseable value is echoed back rather than replaced. This is the single home for what used to be three copy-pasted `priceLabel`s (home, profile, bookmarks) plus the profile page's `formatDate`.
- `app/globals.css` — the token layer plus the wallpaper/preference rules. No `@import "tailwindcss"`, no `@theme inline`. Every colour the two themes disagree on is a custom property written as one `light-dark(light, dark)` pair (`--surface*`, `--ink*`, `--accent*`, `--pill-*`, `--btn-*`, `--overlay-*`, `--focus-ring*`), so components name a surface or an ink instead of a colour and the theme switch is a single `color-scheme` on `<html>`. It also defines `--font-scale`, `--scroll-progress`, the `--on-bg*` foregrounds that track it, and every `data-*` preference rule (see *Accessibility tools*).
- `app/components/ScrollWallpaper.tsx` — `"use client"`, rendered once in `layout.tsx` (outside the page shell, so the colour filters never touch it), so every route shares it. Draws the fixed backdrop (`.scroll-wallpaper`, `z-index: -1`, behind all content) and, from a rAF-throttled scroll/resize/`ResizeObserver` handler, publishes `--scroll-progress` plus the interpolated `--on-bg*` colours on `<html>`. The endpoints it interpolates are read from a hidden probe element with `getComputedStyle`, not hard-coded, so `light-dark()` and `color-mix()` resolve before JS sees them; a `MutationObserver` re-reads them when `data-theme`/`data-contrast` change, and under reduced motion it writes nothing at all. The CSS defaults equal the top-of-page state, so the server HTML and first client render match exactly — no hydration mismatch and no flash.

## Accessibility tools
The bottom of the drawer (`Header.tsx` → `AccessibilityPanel`) carries the whole set, and **Alt+A** opens that drawer with the panel in it from anywhere. Eight controls: theme, colour filter, a text-size **stepper** (− / +), reduce motion, high contrast, read aloud, text spacing, and a Reset that is disabled while everything is at its default. The stepper's own ends disable themselves the same way.

- `lib/prefs.ts` — the contract, shared by the server and the client. `PREFS_COOKIE` (`unifind_prefs`), the unions (`ThemePref` `system|light|dark`, `FilterPref` `off|…|greyscale`, `MotionPref` `system|reduced|full`, `ContrastPref`, `SpacingPref`), `TextSizePref` — which is a **number, not a union**: the step itself, `TEXT_SIZE_MIN` −5 … `TEXT_SIZE_MAX` 5 with 0 normal, so the panel can be a stepper — `DEFAULT_PREFS`, `stepTextSize(current, ±1)` for that stepper, validating `parsePrefs(raw)` (every field checked against its allowed values; anything unknown falls back to the default rather than reaching the DOM — the one deliberate exception is a numeric text size, which is rounded and *clamped* into the scale, because an out-of-range step still plainly means "bigger" or "smaller". The pre-stepper names `normal|large|larger` are still read as steps 0/1/2 so an existing cookie is not silently reset), `prefsAttributes(prefs)` (the `data-theme` / `data-filter` / `data-text` / `data-motion` / `data-contrast` / `data-spacing` set — `data-text` is the step as a string), `isDefaultPrefs` and `writePrefsCookie`. Prefs are **client-only state in a cookie** — no schema, no `getWriteDb()`, no `db:reset`.
- The preference is written onto `<html>` **by the server** in `app/layout.tsx`, and `AccessibilityProvider` only keeps DOM, cookie and React state in step afterwards. That is what makes the theme and the filter right in the first frame with no pre-paint script and no hydration mismatch. `commit()` (state → attributes → cookie) is called from event handlers only, because lint enforces `react-hooks/set-state-in-effect`.
- **The theme is `color-scheme`.** `:root` is `color-scheme: light dark` (which is also what *enables* `light-dark()`), `:root[data-theme="light"|"dark"]` forces one side, and "system" needs no rule at all — the browser follows the OS by itself. So the whole theme switch is one property, and the tokens carry both values in a single pair. On the MUI side the provider has two themes built at module scope and picks one from `resolvedTheme`; `CssBaseline` is rendered with `enableColorScheme={false}` so MUI never writes `color-scheme` and fights the CSS. A dark-OS visitor whose pref is *System* gets the right CSS instantly but the right MUI chrome one hydration frame later — the deliberate cost of not quieting the server's answer.
- **Turbopack's CSS pipeline compiles `light-dark()` away.** Lightning CSS rewrites every pair into `--lightningcss-light`/`--lightningcss-dark` variable flips (visible in the emitted CSS, including in the `data-theme` rules and the `prefers-color-scheme` block), so the tokens also work in browsers that never shipped `light-dark()` natively. Do not "simplify" a token into per-theme copies, and if a rule needs a scheme, set `color-scheme` on `:root` or `:root[data-theme=…]` — that is the switch the transform is keyed to.
- **Colour filters** are `<feColorMatrix>` definitions in `app/components/a11y/ColorFilters.tsx` (standard sRGB CVD matrices), referenced from globals.css by `:root[data-filter="…"] .page-shell { filter: url(#unifind-cvd-…) }`. They target the page shell and not `<html>` on purpose: a `filter` creates a containing block for fixed-position descendants and only the document root is exempt *in the spec*, so a root filter is a gamble on every browser disagreeing differently. The shell is the page's own content; the wallpaper and the read-aloud chip are outside it, and the drawer, dialogs, menus and selects are MUI portals rendered at the body, so nothing that must stay fixed is inside the filtered subtree.
- **Read aloud** (`SpeechOnHover.tsx` + `describeElement.ts`): off by default; when on, hovering any element for 3 s speaks a sentence about it (focus speaks immediately, since keyboard users get no hover). `describeElement` derives role, accessible name and state — `aria-label`, `alt`, associated `label`, visible text, plus disabled/pressed/checked/expanded — rather than reading raw markup. Only one utterance at a time; Escape, a scroll or a pointer press stops it. The highlight ring (`[data-a11y-speaking]`) and the little chip are written **through a ref**, so a hover neither re-renders React nor stacks up state, and the chip is `position: fixed` (outside the shell).
- **Reduced motion** is enforced twice on purpose — the explicit preference and the OS setting under "system" — because the CSS cannot know which one the visitor picked. The CSS kills transitions and animations; `Slideshow` also stops its autoplay interval rather than relying on the CSS, and `ScrollWallpaper` writes no inline variables at all.
- **Text size** is `--font-scale` multiplied into `html { font-size }`, so every `rem` in the app scales together, MUI's typography included — and so the number itself is what the stepper walks up and down. It is **eleven steps, five either side of normal**, written out one rule per step in globals.css (`:root[data-text="-5"]` … `:root[data-text="5"]`): CSS cannot do arithmetic on an attribute value (`attr()` is still not typed everywhere), and spelling each one out is what keeps JS out of the path, so the size is right in the first frame. The ramp is geometric — ×1.1 up, ×0.93 down (0.7 … 1.61) — because an even ramp would make the bottom unusable long before the top was too big. Two consequences: the **drawer width follows the scale** (`min(calc(240px * min(var(--font-scale), 1.5)), 88vw)` in `Header.tsx`), since the drawer holds the panel that does the scaling and its rows would otherwise wrap at the top of the scale; and new sizes anywhere belong in `rem`, not `px` — a few older px values were converted for this.
- **High contrast** is not a second palette — it is the same tokens with the softness removed: muted ink becomes full ink, hairlines become ink, the wallpaper's secondary ink becomes solid, the floating overlay controls stop being translucent, and the ring grows. On top of that, two rules make it obvious at a glance: `:root[data-contrast="high"] .MuiPaper-root { border: 2px solid var(--ink) }` frames every surface there is (cards, the app bar, the drawer, dialogs, menus, popovers, accordions — they are all Papers), and the standard underline plus the outlined search field double in weight. All of it derives from the tokens, so there is no per-theme copy. **Trap:** under high contrast `--ink-line` and `--ink-hairline` both resolve to solid ink, so `--ink-line` may not be used as a *background* — `PostForm`'s disabled submit uses `--surface-inset` for exactly that reason.
- **Landmarks**: the skip link is the first thing in `<body>` and jumps to `#content`; every page root is `<main id="content" tabIndex={-1}>` (on a MUI `Box`, that is `component="main"` — the `tabIndex` is what lets the skip link actually move focus into it), the drawer's nav list is `aria-label="Main"`, and the profile sidebar is an `aside`. Skip-link and 404 pages included; the 404 also takes `tabIndex={-1}` so the focus lands on it rather than staying on the dead link.
- **The app bar is sticky** (`position="sticky"` on the `AppBar`; MUI's own `positionSticky` class supplies `top: 0` and `z-index: 1100`). Two companions live in globals.css, because a sticky bar changes what "scroll this into view" means: `html { scroll-padding-top: 5rem }` and `#content { scroll-margin-top: 5rem }`, so the skip link and any focus jump clear the bar instead of landing under it. The bar is still in flow, so nothing is hidden behind it at rest, and it is a Paper — which is why high contrast frames it too.
- The drawer deliberately **no longer closes on any click or keypress** — it holds live controls now — so each nav row closes it itself (see the `Header.tsx` bullet).
- Deliberately not built: a speech-rate control (the OS voice settings cover it) and social sign-in.

## Auth
- **Every demo account shares the password `unifind123`.** `db/seed.sql` stores a real scrypt hash (fixed salt, so the seed stays byte-for-byte reproducible). The `$2b$…` bcrypt strings that used to be there were truncated fakes and no account could log in.
- The login field accepts **either** the handle or the full email (`josa_organizer` or `josa_organizer@live.iium.edu.my`); an `@` picks the lookup. The handle shown in the UI is the email local-part.
- Handles are a login credential now, so `register()` rejects one that is already taken. Handles are derived from the email local-part rather than stored, so without that check two addresses (`a@x.com` and `a@y.com`) would share one and `getUserByUsername` would return either at random.
- `AUTH_SECRET` is read from the environment and signs the session cookie. There is a hard-coded development fallback so local work needs no setup — set a real `AUTH_SECRET` (e.g. in `.env.local`, which is gitignored) before deploying anywhere.
- Accounts live in the same `data/unifind.db`. Because seeding is non-destructive, they survive restarts; `npm run db:reset` wipes them.
- Lint enforces the React Compiler rule `react-hooks/set-state-in-effect`, so the login flow deliberately has **no effects**: `LoginDialog` calls the server actions from a submit handler and closes itself on success, and the controlled tab lives in `Header`. The one effect in `Header` is the `unifind:auth-prompt` listener, and it only calls its setters from inside an event callback, which the rule allows.

## Posting
- `/post` is a **top-level route**, so `proxy.ts` had to learn it (see the proxy bullet) — otherwise every request there would be treated as a profile lookup and rewritten to a 404.
- Posting is the **third runtime writer** (`getWriteDb()`), after signup and bookmark toggles. No schema change was needed for it, so there was **no `db:reset`** and accounts created at runtime survived.
- The entered wall-clock is stored **verbatim** as `YYYY-MM-DD HH:MM:SS`. The app renders every stored timestamp as UTC (`lib/format.ts`), so what the organiser types is exactly what the site shows afterwards; converting into the browser's zone would display a different time than the one entered. (The `datetime-local` value needs no `Z`-less guessing: it is already "YYYY-MM-DDTHH:MM", the shape the column holds with a space and `:00`.)
- A posted **picture** is written beside the seeded ones under `public/img/` and named after the new record's stem — `Events/event-13.jpg`, `Rental/item-20.jpg`, `Services/service-19.jpg` (a service's stem is `service-<n>`; a rental's is `item-<n>`) — because the name comes from the id, the row is inserted first and its stem column updated after the file lands. Every surface then resolves it through `imageIndex` / `itemImageIndex` with no special case, and a post without a picture keeps the placeholder. If the write fails the row is deleted again, so a post never silently drops the file the author picked.
- **The upload writes into the working tree.** That is what `next dev` and a local `next start` serve, which is enough for this project; a deployment with an immutable or read-only filesystem would need a real object store, since files added at runtime are not part of the build.
- `experimental.serverActions.bodySizeLimit` is raised to `6mb` in `next.config.ts` — the default is **1 MB**, which rejects an ordinary photo before the action ever runs — and `lib/posts.ts` caps the file at 5 MB itself (multipart overhead needs the headroom). Only raster formats are accepted: an uploaded SVG would run its own scripts on this origin.
- Validation lives in `lib/posts.ts` and returns one message at a time, like the login form: required fields, `start < end`, a price of zero or more, a category (including the free-text `Other…` value), the picture's size and extension. A guest is rejected server-side too, even though the page never renders the form for one.
- On success the client `router.push`es to the new record's details page, so the confirmation is the record itself; the action also calls `revalidatePath` for `/` and the author's profile, which only clears the client router cache — every route renders per request anyway.
- The dropdowns come from `getEventCategories` / `getItemCategories` / `getPriceUnits` (distinct values already in the catalogue), and `PostForm` only prettifies the unit for display ("per_day" → "Per day"). The category it sends is stored exactly as the seeded rows store theirs.

## Search
- `/search?q=…` is a **top-level route**, so `proxy.ts` had to learn it too — the same trap as `/post`. The query lives in the URL, so a result page can be reloaded, shared or bookmarked; the page reads it from `searchParams` (a Promise in Next 16), trims it, and `generateMetadata` turns it into the tab title (`photo · Search · UniFind`).
- **The search is not SQL.** `lib/search.ts` (server-only) loads the rows through `getEvents()` / `getItems()` / `getAllUsernames()` and scores them; `lib/searchText.ts` (pure) owns the matching rules. The catalogue is a few dozen rows, so this costs microseconds — and *one* matcher serving the results page, the suggestion list and the cards' "by …" note is what stops those three from disagreeing about what matches. If the catalogue ever grows into the thousands, `lib/search.ts` is what moves to FTS5 — which needs an FTS table, so a schema change and a `db:reset`; think about that before scaling.
- `lib/searchText.ts` matches in three tiers, and a record is in the results only if **every term** lands somewhere (the same token-AND rule the SQL version had, so `photo walk` finds a record carrying both words and no record carrying only one):
  1. **Verbatim** — the term appears as written (`campus` in "Campus Life"). Numbers and short words only ever match here.
  2. **Same stem** — the term and a word reduce to the same stem, compared as "the shorter stem starts the longer one", which is what makes `compete` → "competition" work in *both* directions, `kayaking` → "Kayak", `hammocks` → "Hammock". Deliberately a *light* stemmer: one suffix per word, never below `MIN_STEM` (4) characters, so `the` cannot become `th`.
  3. **One edit away** — `keybord` still finds "keyboard". Only for terms of `FUZZY_MIN` (5) characters or more, so a typo in a short word cannot drag half the catalogue in.
- **Terms split on anything that is not a letter or a number**, so `photo-walk` is two words and `%`/`_` are literal characters rather than wildcards (a query of nothing but punctuation has no terms and finds nothing). Tokens are capped (`MAX_TERMS`) so a pasted paragraph cannot build an unbounded query.
- **Organiser/provider names are searched.** `eventFields`/`itemFields` add the poster's handle (`handleOf(email)` — the email local-part, the same rule as `USERNAME_SQL`) as a field of its own, so `josa` finds everything `josa_organizer` posted. A card cannot show why it matched, so the search page says so: `eventCards`/`itemCards` take an optional fourth `note` callback and **only** the search page passes one ("by josa_organizer"). Every other surface builds its cards without it, which is what keeps a record looking the same wherever it is found.
- **People are results too.** The page grows a **People** section (chips linking to `/[username]`, labelled `Organiser` / `Provider` / `Organiser & provider` / `Member` from what that account has posted) whenever a handle matches, and the count line counts them alongside the records ("5 matching records, and 1 person."). No records *and* no people gets the explanatory line instead; an empty query short-circuits *before* any query or image work into a page that explains what search covers.
- The results page reuses `cardData.ts` + `ItemCard`, so a result *is* the home card, and groups them the way the home tabs split the catalogue — **Events**, **Rentals**, **Services** (items split on `item_type`), each under its own `h2` as an `overline` Typography. An empty group renders nothing. Guests search exactly like members — the bookmark control on a result card is a guest's, i.e. it raises the login prompt.
- **As-you-type suggestions** are `GET /api/suggest?q=…` → `{ suggestions: [{ label, hint, href }] }` (`app/api/suggest/route.ts`): records *and* matching people, ranked by the one scoring function, capped at `SUGGEST_LIMIT`, and empty below `MIN_QUERY_LENGTH` (2) characters. It is the app's **only route handler** — the box needs an answer without a navigation, and a suggestion is the same for everyone (no session, no bookmark state), so it is an unauthenticated GET with `cache-control: no-store` (the catalogue can change at runtime — `/post` writes rows — and a stale suggestion is worse than a round trip). Its path is multi-segment, so `proxy.ts` passes it through untouched — the username branch only ever sees single-segment paths.
- The header box is a MUI **`Autocomplete`** (`freeSolo`, `value={null}`, controlled `inputValue` + `open`), not a form: MUI supplies the combobox roles, the keyboard (arrows, Enter, Escape) and the popup, while the ranking stays the server's (`filterOptions` returns the options unchanged). Typing is debounced (`SUGGEST_DELAY_MS`) and every request aborts the last one, so a slow answer for an abandoned prefix cannot overwrite a newer one; the debounce timer and its request are cancelled in one unmount cleanup. Picking a suggestion pushes its `href` (the record or the profile); free text — Enter on something no suggestion matches, or the magnifier, which is now a plain `IconButton` because there is no form left to submit — pushes `/search?q=<encoded>`. On a pick the box keeps the typed text: the URL, not the field, is what records a search. Header deliberately **never reads the URL back** for the same reason as before (`useSearchParams` would drag a `Suspense` boundary onto *every* route).
- Deliberately not built: highlighting the matched words in a card or a suggestion (the organiser note covers the one match a card cannot otherwise explain).

## Hard-learned gotchas (these caused real build/runtime errors)
- MUI styling is Emotion-based; it **requires** `<AppRouterCacheProvider>` (from `@mui/material-nextjs/v16-appRouter`) wrapped around `{children}` in `layout.tsx`. Without it, Emotion injects inline `<style data-emotion>` tags into `<body>` during SSR and React throws "Hydration failed because the server rendered HTML didn't match the client". Keep the package version in lockstep with `@mui/material` (both `9.5.0`).
- A `"use client"` provider between `layout.tsx` and the pages is fine — that is exactly what `AccessibilityProvider` is — but **a MUI theme object must not cross the Server → Client boundary**: passing one as a prop during prerendering throws "multiple renderers" / "Unexpected Fiber popped". Create the theme *inside* the client module (both themes here are module-scope constants in `AccessibilityProvider.tsx`) and hand the client component only plain data (`prefs`). The old version of this note said to keep `ThemeProvider` in `Header.tsx`; the real rule was always the theme object, not the wrapper.
- Do **not** call hooks at module scope in a Client Component (`useMemo` at file level threw "Invalid hook call"). `createTheme()` at module scope is fine — no hook needed.
- No `tailwind.config.js` ever existed (Tailwind v4 configured via CSS import). Do not re-add `@import "tailwindcss"` or Tailwind utility classes; the build has no Tailwind loader.
- MUI v9 removed the deprecated **system props** from components. `alignItems`, `justifyContent`, `mb`, `display`, etc. are **not** valid direct props (TS error: "Property 'alignItems' does not exist on type … StackOwnProps"). Put them in `sx` instead: `<Stack direction="row" spacing={1} sx={{ alignItems: "center" }}>`. Component-owned props still work directly (`direction`/`spacing` on Stack, `variant`/`color` on Typography, `underline` on Link).
- MUI v9 also renamed the internal classes the docs and Stack Overflow answers use. `Tabs` renders `MuiTabs-list`, **not** the old `MuiTabs-flexContainer`, so `sx={{ "& .MuiTabs-flexContainer": … }}` silently does nothing. Reach for `.MuiTabs-list` to style the tab strip. (`centered` + `variant="scrollable"` is still a rejected combination that warns, hence centring through the list class.)
- `displayEmpty` on a `Select` only changes what the field **displays** — it does not mark the `FormControl` as filled, so the floating label stays in the placeholder position and sits *on top of* the placeholder text. `InputLabel`'s shrink is `shrink ?? (filled || focused)`, so the fix is to pin it: `slotProps={{ inputLabel: { shrink: true } }}`. `PostForm`'s category and price-unit selects and its two `datetime-local` fields all do this, since each always shows content of its own.
- `AccordionSummary` has **no default expand icon** in MUI v9 (and there is no `@mui/icons-material` here to borrow `ExpandMore` from), so a bar with no `expandIcon` shows no chevron at all. `app/components/details/Chevron.tsx` supplies one; the rotation is already built in — the styled expand-icon wrapper carries `&.Mui-expanded { transform: rotate(180deg) }`, so a plain chevron animates by itself. The wrapper's own `color: action.active` wins over inherited colour, so recolour through `& .MuiAccordionSummary-expandIconWrapper`. A rounded standalone bar also needs `"&:before": { display: "none" }` (MUI's hairline divider) and `margin: 0` plus `&.Mui-expanded { margin: 0 }`, or the expanded bar jumps.
- **MUI v9's `Autocomplete` `renderInput` hands you `slotProps`, not `InputProps`.** `AutocompleteRenderInputParams` is `{ id, disabled, fullWidth, size, slotProps: { inputLabel, input: { ref, className, startAdornment, endAdornment, onMouseDown }, htmlInput } }`, so the magnifier goes in `slotProps.input.startAdornment` — and any merge has to keep `slotProps.input.className` (`MuiAutocomplete-inputRoot`) and `endAdornment` (the clear button lives in there) or the field loses MUI's own styling. The v5-era `<TextField {...params} InputProps={{ … }} />` from Stack Overflow does not compile. A single-select has no `startAdornment` of its own, so replacing it is safe.
- **An `Autocomplete` inside a `<form>` double-submits.** With `freeSolo` and a single value, Enter calls `preventDefault()` only when it is selecting a *highlighted option*; on free text it calls `onChange(value, "createOption")` and lets the key event through, so a wrapping form would submit too and push twice. That is why the header's box is not a form: the magnifier is a plain `IconButton` and Enter is handled in `onChange`.
- **`value` has to stay `null`** (`value={null}` with a controlled `inputValue`) for free-text Enter to work at all: any non-null value equal to the input makes `inputValueIsSelectedValue` true and MUI skips its freeSolo branch, so Enter does nothing at all. `freeSolo` also suppresses the popup indicator (`hasPopupIcon` is false, so no second arrow appears in the field) and the "invalid value" warning, and the clear button still appears by itself once the box is dirty.

- `export const dynamicParams` is **not allowed** with `cacheComponents` (build error: `Route segment config "dynamicParams" is not compatible with nextConfig.cacheComponents`). Without it, unknown dynamic params render on demand; use `proxy.ts` when you need a real 404 status.
- Reading the session cookie makes a route dynamic, and `cacheComponents` refuses to prerender it (build error: `Next.js encountered uncached or runtime data during prerendering`). The fix lives in **one place**: `app/layout.tsx` exports `instant = false`, which opts the whole app into blocking dynamic rendering instead of streaming. Put it there and not on individual pages — `app/not-found.tsx` is a special file that cannot declare its own segment config, so the `/_not-found` route only passes because the root layout covers it. Every route now reports as `ƒ (Dynamic)`; this is the deliberate trade-off for having the correct guest/signed-in state in the first paint rather than flashing a guest UI. (The alternatives are wrapping the header in `<Suspense>`, or reading the session client-side after mount.)
- **Root `instant = false` does *not* silence the dev-only `instant` insights.** Those are resolved per route *tree* (`app-render/instant-validation/instant-config.js` → `anySegmentNeedsInstantValidation`): a `false` segment opts out of validation for itself only, then the walk continues, and every `page`/`default` segment with no explicit `instant` export is validated implicitly at the default `warning` level. The `isPageAllowedToBlock` path that the `false` *does* drive is consulted only for `allowEmptyStaticShell`, i.e. the build-time static-shell check. So dev shows `Route "/[username]": … encountered URL data…` for `await params` (and the runtime-data variant for `cookies()`), even though blocking is exactly what this app wants. Fixed app-wide with `experimental.instantInsights.validationLevel: 'manual-warning'` in `next.config.ts` — only segments opting in with `export const instant = true` are validated then. Dev-only either way: `next build`/`next start` are unaffected.
- `notFound()` reached after PPR/streaming has started keeps the response at **200** (Next adds `<meta name="robots" content="noindex">`). For a real 404, run the check before the render — i.e. in `proxy.ts`. Where nothing has streamed yet the page's own call does set the status: with the root `instant = false` blocking the render, `/details/<unknown>` answers **404** (verified for both a malformed id and an out-of-range one), so only `/details` needs no proxy branch.
- MUI's polymorphic `component` prop takes a *function*, which cannot cross a Server → Client boundary (`Functions cannot be passed directly to Client Components`). In a Server Component prefer MUI's native `href` (renders an `<a>`) or `next/link`; do not use `component={Link}`.
- `@types/node` must stay at `^24` — the `node:sqlite` types (`DatabaseSync`) do not exist in older versions.
- Anything rendered **directly on the page background** must use `var(--on-bg)` / `var(--on-bg-muted)` / `var(--on-bg-line)` — not a hex, not `text.primary`/`text.secondary`. The wallpaper fades to deep forest green as you scroll, so hard-coded dark colours vanish near the bottom. And anything on a *surface* (a `Card`, the drawer, the app bar, the details bars) uses that surface's own ink — `var(--surface)` / `var(--surface-2)` / `--surface-3` with `var(--ink)` / `var(--ink-muted)` / `var(--ink-line)`, `--pill-*` for the green pills, `--btn-*` for the one filled button, `--overlay-*` for controls floating on a picture. **Prefer the tokens over MUI palette defaults** even where the palette is reachable: the tokens are resolved by `color-scheme` in the very first frame, while MUI's mode comes from JS and can be one frame behind for a *System* visitor on a dark OS.
- Page content **is** inside a theme provider now (`AccessibilityProvider` sits above the pages in `layout.tsx`, so an unstyled MUI component does pick up the site palette) — but the theme only *is* the site palette via those two themes, and it is the light or dark one depending on the resolved mode. An explicit `--btn-*`/`--ink*` colour is still the right way to match the tokens; `BookmarksGuest`'s button and `LoginDialog`'s submit do exactly that.

## Verifying SSR style placement
All `data-emotion` `<style>` tags belong in `<head>`, and **zero** in `<body>`. A body-level `data-emotion` tag means the Emotion cache is misconfigured.

The old way to check this — reading `.next/server/app/index.html` after a build — no longer works: with `instant = false` every route is dynamic, so that file (and `bookmarks.html`, etc.) is written **0 bytes** and the check silently passes on nothing. Check the live server instead:

```powershell
node -e "fetch('http://localhost:3000/').then(r=>r.text()).then(h=>{const b=h.slice(h.indexOf('<body'));console.log('body data-emotion:',(b.match(/data-emotion/g)||[]).length)})"
```

Also watch the browser console for `Hydration failed` / `did not match` while loading the pages — that is the symptom the placement rule prevents.

Search and the suggestion endpoint have their own battery, and each line is checking a different tier of the matcher:

```powershell
node -e "for (const q of ['compete','competition','competing','keybord','josa','josa_organizer','campus photography','photo_studio','%','_']) fetch('http://localhost:3000/api/suggest?q='+q).then(r=>r.json()).then(j=>console.log(q, '->', j.suggestions.map(s=>s.label+' ['+s.hint+']').join(' | ') || '(none)'))"
```

`compete` / `competition` / `competing` must return the **same** records (the stem tier), `keybord` must still find the keyboards (the one-edit tier), `josa` and `josa_organizer` must return the handle *and* that account's records (organiser matching — the underscore is just a word break), `campus photography` must return only the records where **both** words land somewhere (one on a title, one through its provider's handle), `photo_studio` must return the provider plus its services, and `%` / `_` must return nothing at all — they are literal characters, not wildcards. A query below `MIN_QUERY_LENGTH` and an empty `q` must both come back `{ "suggestions": [] }`, and `/api/suggest` must answer **200 JSON**, not a 404 page (that is the proxy proving it treats a two-segment path as a route, not as a username). On `/search`, a matching handle puts a `by <handle>` caption under the affected cards' subtitle and a People chip (`josa_organizer · Organiser & provider`), and the count line reads "5 matching records, and 1 person." — the chips and the captions come from the same `scoreText`, so if they disagree, the annotation rule drifted.

The same fetch covers the accessibility plumbing: a cold request must carry all six attributes on `<html>` (`data-theme="system" data-filter="off" data-text="0" data-motion="system" data-contrast="normal" data-spacing="normal"`), a hand-made `unifind_prefs` cookie must change exactly those, and a cookie with bogus values must come back as the defaults — `parsePrefs` is the only thing standing between a cookie and the DOM, so re-check it with a hostile cookie whenever a preference is added. For the text size specifically: `3` and `"3"` must arrive as `data-text="3"`, `99` / `-99` must clamp to `"5"` / `"-5"`, the legacy `"large"` / `"larger"` names must come back as `"1"` / `"2"`, and `"huge"` / `true` / an object must all fall back to `"0"` — a boolean must not be coerced into step 1.

Two things to know before grepping the CSS: Turbopack's Lightning CSS **compiles `light-dark()` away** into `--lightningcss-light`/`--lightningcss-dark` flips and normalises colours (`#D8F3DC` → `#d8f3dc`, `rgba(…)` → `#081c150d`), so grepping for the source text finds nothing even when the rule is present — search the selector or the custom-property name instead; and MUI's **portals render `null` on the server**, so the drawer, dialogs and dropdowns never appear in the SSR HTML no matter what `open` is. To inspect one, temporarily render the component into a page body (it works in SSR; `Portal` does not).

## Paths / imports
- `@/*` maps to repo root (tsconfig `paths`).
- Slideshow images live in `public/img/trending/` and are auto-discovered at build time: `app/page.tsx` (Server Component) reads the folder with `fs.readdirSync` and passes `Slide[]` (`{ id, href, src }`) to `<Slideshow slides={...} />`. Drop a new image in `public/img/trending/` (no code change) — the count drives nothing but how many dots the window scrolls through. - **`Slideshow.tsx` is a coverflow stage, not a 3D ring.** The active slide sits flat in the middle; its two neighbours lean away from the camera (a plain `rotateY` about each panel's own centre, so the browser's perspective projection does the widening/narrowing) and every other slide waits further out at `opacity: 0` — that parked position is what makes a change animate instead of snap. **The lean points away from the middle**, so the neighbours' *inner* edges (the ones beside the arrows) are the tall, close ones and their outer edges fall away small: that is the deliberate reverse of the classic coverflow look. Flipping the sign is a one-character change in `coverflowTransform`, but be aware it moves everything else too — with the panels facing outward the far edge recedes, which pulls the silhouette *inward*, so the same constants give a much smaller overhang off the screen edge and a gap between the arrow and the panel. The direction was re-tuned after the flip (`TILT_DEG`/`SIDE_SCALE`/`SIDE_SHIFT`) to buy the overhang back.
- Frames and dots use `FRAME_COLOR` = `var(--surface-2)`, the same token the app bar's `colorDefault` override uses — so the frame still copies the header's neutral rather than a hard-coded black or white, and it follows the theme. Keep them in step if that token ever moves. The dots are a hair lighter than the wallpaper's top gradient, so their `boxShadow` is what actually gives them an edge — do not drop it. The arrows sit on the pictures, so they use the `--overlay-*` set (translucent surface + ink) rather than `FRAME_COLOR`.
- **The cooldown (`NAV_LOCK_MS`) is a dead zone, in both directions.** The arrows are `disabled` while `locked`, which is what makes them look inert — but MUI's own disabled rule is `pointer-events: none`, and the arrows sit exactly over the neighbouring panel, so a stray click used to fall straight through the arrow onto *that* slide's link and open the wrong record. Two rules stop it: the arrows re-enable `pointerEvents` and pin `cursor: default` in their `&.Mui-disabled` block (owning their square instead of passing the pointer on, exactly as the dots' cursor does), and the slides' stretched `<Link>` is `pointerEvents: none` while `locked`, so nothing on a moving stage can be activated. That is pointer-only — keyboard activation is untouched. Note the lock is deliberately shorter than the 0.85 s panel transition (overlapping moves are fine); autoplay still bypasses the lock entirely, so the stage stays live during an autoplay tick.
- Two couplings matter in the stage: the section is deliberately **full bleed** (`overflow: hidden`, no `maxWidth`) because the neighbours have to run off the screen edges — do not slot it back into the 1400px content column the rest of the page uses; and `SIDE_SCALE` is what keeps the neighbours inside the stage. With the lean pointing outward the magnified corner is the **inner** one, so the ceiling is `PERSPECTIVE / (PERSPECTIVE - sin(TILT) * w * S / 2) < 1 / SIDE_SCALE` — that is why `SIDE_SCALE` cannot go much above 0.9, and why widening the `clamp()` ceiling for `--slide-w` without lowering it starts clipping the tall inner edges against the stage's top and bottom. The `layout-check` helper measures this directly as `clipped`. Because the slides are `position: absolute` inside the stage (not children of a transformed ring), `pointerEvents` is switched off for the off-stage ones — an invisible panel that still takes clicks is a trap sitting over the frame.

- **Header logo.** `Header.tsx` renders `public/img/logo-wordmark.png` (the `UniFind` wordmark with a magnifying glass for the `d`) at a fixed 32px height, linked to `/`. That file is a **cropped derivative** of `public/img/logo.png`: the original is 604×478 but the actual wordmark ink is only 457×157, so rendering it directly at header height would make the text illegibly small. `logo.png` is kept untouched; regenerate the crop with `System.Drawing` if the wordmark changes.
- **Image naming is the identifier.** Every event/item has a canonical record id `<kind>-<n>` (`event-1`, `item-4`), and its picture is named after that stem: `public/img/Events/event-1.jpg`. `events.banner_image_url` and `items.images` store the stem (`'event-1'`, `'item-4'`) and each page builds a `stem -> URL` index (`imageIndex(folder)`) so it looks rows up **by name** — inserting or reordering rows can never shift which picture a card gets. Items sit in a folder chosen by type, so a rental is `item-<n>` in `public/img/Rental/` but a service is `service-<n>` in `public/img/Services/`; both pages resolve items through `itemImageIndex()`, which merges the two folders into one stem index. A picture uploaded through `/post` is written the same way, named after the id the insert just produced (see *Posting*). A row whose stem has no file renders the blank placeholder. Text-image order and `public/img/*.png` (legacy) are no longer used.
- `app/details/[id]/page.tsx` — the Details route, keyed by the record id (`/details/event-1`, `/details/item-10`). The Server Component resolves the record with `parseRecordId` + `getEventById`/`getItemById`, resolves its picture through `imageIndex("Events")`/`itemImageIndex()`, folds in the provider's user row and the viewer's bookmark state, and hands `DetailsView` already-formatted data (`DetailsData` — plain strings, so the whole page passes the Server → Client boundary). `generateMetadata` takes the title and description from the record itself. `generateStaticParams` prerenders every known id (events via `getEvents()`, plus **all** items via `getItems()` — services included, since `getRentals()` alone would leave them as on-demand params); unknown ids `notFound()`.
